## 📋 方案总览

我们提供了 **3种完整的部署方案**，适用于不同场景：

| 方案 | 名称 | 使用场景 | 推荐度 | 部署时间 |
|------|------|---------|--------|---------|
| **方案1** | 本地编译+上传 | 日常开发，SSH可用 | ⭐⭐⭐⭐⭐ | 2分钟 |
| **方案2** | Git提交编译产物 | SSH不可用，紧急情况 | ⭐⭐ | 1分钟 |
| **方案3** | 服务器端编译 | 服务器有Node.js环境 | ⭐⭐⭐⭐ | 3分钟 |

## 🚀 方案1: 本地编译+上传（推荐）

### 工作原理

```
Windows本地执行
    ↓
1. 本地编译H5 (npm run build:h5)
    ↓
2. 压缩成 h5-upload.zip
    ↓
3. 通过SSH上传到服务器 (scp)
    ↓
4. 通过SSH触发服务器部署脚本
    ↓
5. 服务器解压并部署到Nginx目录
```

### 优缺点

**优点**:
- ✅ 服务器不需要Node.js环境
- ✅ 本地可以快速测试编译结果
- ✅ 编译失败不影响服务器
- ✅ Git仓库保持小巧（仅源代码）

**缺点**:
- ⚠️ 需要SSH连接
- ⚠️ 需要本地Node.js环境

### 使用方法

#### 完整部署（前端+后端）

```batch
cd D:\your-mcp-proxy\AITY_VIP\aity-uni-app-v2\scripts
full-deploy.bat
```

**自动执行**:
1. ✅ 本地编译H5
2. ✅ 压缩并上传到服务器
3. ✅ 更新后端代码
4. ✅ 重启后端服务
5. ✅ 部署前端到Web目录

**时间**: 约2分钟

#### 仅更新后端（快速修复）

```batch
cd D:\your-mcp-proxy\AITY_VIP\aity-uni-app-v2\scripts
deploy-backend.bat
```

**时间**: 约30秒

#### 仅更新前端

```batch
cd D:\your-mcp-proxy\AITY_VIP\aity-uni-app-v2\scripts
upload-h5-to-server.bat
```

**时间**: 约1分钟

### 适用场景

- ✅ **日常开发**: 前后端一起更新
- ✅ **前端优化**: 仅更新前端UI
- ✅ **快速修复**: 仅更新后端逻辑
- ✅ **Git仓库大小敏感**: 保持仓库小巧

## 🔧 方案2: Git提交编译产物（备用）

### 工作原理

```
Windows本地
    ↓
1. 修改.gitignore允许提交dist/
    ↓
2. 本地编译 (npm run build:h5)
    ↓
3. 提交编译产物到Git (git add dist/)
    ↓
4. 推送到远程 (git push)
    ↓
服务器
    ↓
5. 拉取代码 (git pull)
    ↓
6. 自动包含编译产物
    ↓
7. 复制到Nginx目录
```

### 优缺点

**优点**:
- ✅ 不需要SSH连接
- ✅ Git拉取后直接可用
- ✅ 操作简单

**缺点**:
- ❌ Git仓库体积增大（7-15MB每次提交）
- ❌ Git push/pull变慢
- ❌ 代码审查困难（大量diff）
- ❌ 不适合频繁部署

### 使用方法

#### 第一次配置

```bash
# 1. 切换.gitignore配置
cp .gitignore .gitignore.backup
cp .gitignore.allow-dist .gitignore

# 2. 编译并提交
npm run build:h5
npm run build:mp-weixin

git add dist/
git commit -m "chore: 添加编译产物到Git"
git push origin feature/iteration-1

# 3. 服务器端拉取并部署
ssh root@111.48.74.245 "cd /tmp/AITY/aity-uni-app-v2 && git pull && cp -r dist/build/h5/* /var/www/html/h5/ && chown -R www-data:www-data /var/www/html/h5"
```

#### 日常使用

```bash
# 1. 修改代码并编译
npm run build:h5

# 2. 提交（包含源代码和编译产物）
git add .
git commit -m "feat: xxx"
git push origin feature/iteration-1

# 3. 服务器拉取
ssh root@111.48.74.245 "cd /tmp/AITY/aity-uni-app-v2 && git pull && cp -r dist/build/h5/* /var/www/html/h5/"
```

#### 恢复默认配置

```bash
# 恢复.gitignore
cp .gitignore.backup .gitignore

# 从Git移除编译产物
git rm -r --cached dist/
git commit -m "chore: 恢复默认配置"
git push origin feature/iteration-1
```

### 适用场景

- ✅ **SSH不可用**: 网络受限或SSH被阻断
- ✅ **紧急部署**: 需要快速推送更新
- ❌ **日常开发**: 不推荐（Git仓库会很大）

## 🖥️ 方案3: 服务器端编译（折中）

### 工作原理

```
Windows本地
    ↓
1. 提交源代码到Git
    ↓
2. 通过SSH触发服务器编译
    ↓
服务器
    ↓
3. 拉取最新代码 (git pull)
    ↓
4. 服务器端编译 (npm run build:h5)
    ↓
5. 自动部署到Nginx目录
```

### 优缺点

**优点**:
- ✅ 不需要上传编译产物
- ✅ 本地不需要Node.js环境
- ✅ Git仓库保持小巧
- ✅ 一键触发，自动化完成

**缺点**:
- ⚠️ 服务器需要Node.js环境
- ⚠️ 编译占用服务器资源
- ⚠️ 编译时间较长（约3分钟）

### 使用方法

#### 首次配置：服务器端准备

**1. 安装Node.js环境**（您正在进行中）

```bash
# SSH到服务器
ssh root@111.48.74.245

# 安装Node.js 18.x
curl -fsSL https://deb.nodesource.com/setup_18.x | bash -
apt-get install -y nodejs

# 验证安装
node -v
npm -v
```

**2. 上传服务器端编译脚本**

```bash
# 在Windows本地执行
scp D:\your-mcp-proxy\AITY_VIP\aity-uni-app-v2\scripts\server-build-and-deploy.sh root@111.48.74.245:/tmp/AITY/build-and-deploy.sh

# SSH到服务器添加执行权限
ssh root@111.48.74.245 "chmod +x /tmp/AITY/build-and-deploy.sh"
```

**3. 首次编译需要安装依赖**

```bash
# SSH到服务器
ssh root@111.48.74.245

# 首次编译会自动安装依赖
bash /tmp/AITY/build-and-deploy.sh
```

#### 日常使用

```batch
REM Windows本地执行
cd D:\your-mcp-proxy\AITY_VIP\aity-uni-app-v2\scripts
deploy-server-build.bat
```

**自动执行**:
1. ✅ 提交源代码到Git
2. ✅ 触发服务器端编译
3. ✅ 服务器拉取代码
4. ✅ 服务器编译H5
5. ✅ 自动部署到Nginx

**时间**: 约3分钟

### 适用场景

- ✅ **服务器有Node.js**: 已安装或愿意安装
- ✅ **本地环境受限**: 本地Node.js环境问题
- ✅ **简化流程**: 不想本地编译再上传
- ⚠️ **服务器性能充足**: 编译不影响线上服务

| **Git拉取速度** | 快 | 慢 | 快 |
| **编译失败影响** | 本地 | 本地 | 服务器 |

## 🎯 方案选择决策树

```
开始
  ↓
SSH是否可用？
  ├─ 否 → 使用方案2（Git提交编译产物）
  └─ 是 ↓
      服务器是否有Node.js环境或愿意安装？
      ├─ 是 → 使用方案3（服务器端编译）或方案1
      └─ 否 ↓
          使用方案1（本地编译+上传）【默认推荐】
```

### 推荐使用顺序

1. **首选**: 方案1（本地编译+上传）
   - 最成熟、最可靠
   - 服务器资源占用少
   - Git仓库保持小巧

2. **次选**: 方案3（服务器端编译）
   - 如果服务器已安装Node.js
   - 如果本地Node.js环境有问题
   - 如果不想本地编译

3. **备用**: 方案2（Git提交编译产物）
   - 仅在SSH不可用时
   - 仅在紧急情况下
   - 不推荐作为常规方案

## ✅ 编译校验机制

我们已为您实现了 **两层编译校验**：

### 层级1: 本地开发启动时校验

```bash
# 启动开发服务器时会自动检查
npm run dev:h5

# 如果没有编译产物，会提示：
# ⚠️  警告：未发现编译产物！
# 建议执行: npm run build:h5
# 或者直接开发: npm run dev:h5
```

### 层级2: 手动检查编译产物

```bash
# 检查所有编译产物
npm run check:build

# 输出示例：
# ✅ 所有编译产物检查通过
#   - H5编译产物: ✅ 存在
#   - 小程序编译产物: ✅ 存在
```

### 层级3: 服务器部署脚本校验

服务器端脚本会自动检查：
- 方案1: 检查 `/tmp/h5-upload.zip` 是否存在
- 方案3: 检查编译产物 `dist/build/h5/index.html` 是否存在

如果校验失败，会给出明确的错误提示。

## ❓ 常见问题

### Q1: 三个方案可以混用吗？

**A**: ✅ **可以！** 三个方案完全兼容，可以根据不同场景灵活切换：
- 日常用方案1
- 服务器安装Node.js后用方案3
- SSH出问题时临时用方案2

### Q2: 方案1的SSH连接断了怎么办？

**A**:
- 重新执行 `full-deploy.bat` 即可
- 或切换到方案3
- 或临时使用方案2

### Q3: 方案3的编译会影响线上服务吗？

**A**:
- 编译过程会占用服务器CPU和内存
- 但不会影响已运行的Nginx服务
- 编译完成后自动替换静态文件
- 建议在低峰期使用方案3

### Q4: 如何确认部署成功？

**A**:
```bash
# 1. 检查后端
ssh root@111.48.74.245 "pm2 status aity-backend"
# 应显示: online

# 2. 检查前端
ssh root@111.48.74.245 "ls -la /var/www/html/h5/index.html"
# 应显示文件信息

# 3. 访问测试
# 浏览器打开: http://111.48.74.245/h5/
```

### Q5: 编译失败怎么办？

**A**:
- **方案1**: 本地编译失败，查看错误信息，修复后重新编译
- **方案3**: 服务器编译失败，查看日志 `pm2 logs aity-backend`，修复后重新触发
- **通用**: 查看编译错误信息，检查代码语法，确认依赖是否完整
