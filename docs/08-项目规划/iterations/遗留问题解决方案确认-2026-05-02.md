## 三、核心设计决策

### 3.1 决策一：不要把“互动交流”塞进 `discussions.status`

**背景**  
当前前端 “互动交流” tab 使用 `value: 'feedback'`，请求后端时传入 `status=feedback`。但后端 `Discussion` 模型中 `status` 只有 `pending`、`replied`。文档中提出的修复方案是给 `status ENUM` 增加 `feedback`。

**问题**  
`status` 的语义是处理状态，表示“待回复/已回复”。“互动交流”是讨论类别或业务场景，不是处理状态。如果把 `feedback` 加入 `status`，会出现语义冲突：一条互动交流被回复后状态应该是 `replied`，但它又需要继续属于“互动交流”。这会导致筛选逻辑互相覆盖。

**推荐方案**  
新增讨论分类字段：`discussions.category`。

```sql
ALTER TABLE discussions
ADD COLUMN category VARCHAR(50) NOT NULL DEFAULT 'interaction' COMMENT '讨论分类：interaction=互动交流'
AFTER status;

UPDATE discussions
SET category = 'interaction'
WHERE category IS NULL OR category = '';
```

**字段职责**

| 字段 | 职责 | 示例值 |
|------|------|------|
| `status` | 处理状态 | `pending`, `replied` |
| `category` | 讨论分类 | `interaction` |
| `visibility` | 可见范围 | `private`, `public` |

**影响文件**

| 文件 | 预期改动 |
|------|------|
| `backend/src/models/Discussion.js` | 增加 `category` 字段 |
| `backend/src/controllers/discussionController.js` | 查询支持 `category`，创建讨论默认 `interaction` |
| `aity-uni-app-v2/src/pages/discussions/discussions.vue` | “互动交流”从传 `status=feedback` 改为传 `category=interaction` |
| `aity-uni-app-v2/src/api/discussion.js` | 如当前 API 封装透传 params，可不改；否则补 `category` |
| `backend/migrations/20260502-add-discussion-category.sql` | 新增迁移脚本 |

## 四、备选方案对比

### 4.1 “互动交流”筛选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|

**推荐采用方案 B。**

## 五、分问题解决方案

### 5.1 L1：“互动交流”筛选无效

**根因**
- 前端 `discussions.vue` 中 “互动交流” 使用 `value: 'feedback'`。
- 后端 `getDiscussions` 将 query 中的 `status` 直接写入 `where.status`。
- 数据模型 `status` 不存在 `feedback`，且不应承载“类别”语义。

**目标行为**
- 点击“互动交流”后，展示 `category=interaction` 的讨论。
- 点击“待回复”后，展示 `status=pending` 的讨论。
- 点击“已回复”后，展示 `status=replied` 的讨论。
- “互动交流”和“待回复/已回复”后续可以组合扩展，但本轮不强制实现组合筛选。

**验收标准**
- [ ] “互动交流” tab 能展示讨论列表。
- [ ] “待回复” tab 仍展示 `pending` 数据。
- [ ] “已回复” tab 仍展示 `replied` 数据。
- [ ] 创建新讨论后默认进入“互动交流”，状态为“待回复”。
- [ ] 管理员回复后，该讨论仍属于“互动交流”，同时状态变为“已回复”。

### 5.2 L2：图片 404

**根因**
- 数据库记录来自生产或云端环境。
- 图片文件保存在对应后端的 `backend/uploads/images/`。
- 本地后端静态目录没有这些文件，因此 `/uploads/images/...` 返回 404。

**推荐方案**
- 短期：保留前端图片加载失败占位图。
- 根治：同步生产/云端 `backend/uploads/images/` 到本地测试环境，或重新导入一套包含本地图片资源的测试数据。
- 增强：提供上传资源一致性检查脚本，扫描数据库附件 URL 与文件系统是否一致。

**不建议**
- 不建议在前端用生产域名兜底加载本地缺失图片。这样会掩盖环境问题，也可能导致测试环境误依赖生产资源。

**验收标准**
- [ ] 本地消息详情页不再出现已知生产图片 404。
- [ ] 缺失图片仍能显示占位图，不打断用户操作。
- [ ] 新上传图片能在当前 API 环境对应的 `/uploads/images/` 下找到。

---

### 5.3 L3：图片上传后本地文件不存在

**根因假设**
- 前端上传地址由 `API_BASE_URL + '/upload'` 决定。
- `dev/build:*:local` 应连接本地后端。
- `dev/build:*:cloud` 应连接云端后端。
- 如果运行脚本或 `.env` 不一致，就会出现“数据库看的是本地，文件上传到云端”或反向错配。

**推荐方案**
- 明确本地开发只使用：`npm run dev:mp-weixin:local`。
- 明确云端联调只使用：`npm run dev:mp-weixin:cloud`。
- 在上传成功日志中输出当前 `API_BASE_URL`、返回 URL、文件名，便于定位环境。
- 在文档和测试步骤中要求上传后检查对应环境的 `backend/uploads/images/`。

**验收标准**
- [ ] local 模式上传后，本地 `backend/uploads/images/` 出现文件。
- [ ] cloud 模式上传后，云端 `backend/uploads/images/` 出现文件。
- [ ] 前端日志能明确显示本次上传目标 API 环境。

### 5.4 L4：消息类型筛选无内容

**根因**

### 5.5 L5：生产数据库 `messages.type` 变更

**根因**
- 测试环境已执行 `messages.type ENUM -> VARCHAR(50)`。
- 生产环境仍需按流程手动执行。

**推荐方案**
- 补充 migration 文件，不只依赖迭代总结中的手工 SQL。
- 迁移先在测试库执行并验证，再在生产库执行。

**建议 migration**

```sql
-- backend/migrations/20260502-message-type-varchar.sql
ALTER TABLE messages
MODIFY COLUMN `type` VARCHAR(50) NOT NULL DEFAULT 'daily' COMMENT '消息类型';
```

**验收标准**
- [ ] 测试库 `messages.type` 为 `VARCHAR(50)`。
- [ ] 生产库 `messages.type` 为 `VARCHAR(50)`。
- [ ] 发布自定义消息类型不再因 ENUM 限制失败。
- [ ] 删除自定义类型并迁移旧消息时不报错。
