## 🎯 项目目标与限制

### 核心目标
- ✅ **支持 H5 网页部署**
- ⏳ **计划支持小程序部署**（微信、支付宝、百度、字节跳动等）
- ✅ **满足用户需求**

### 当前限制
- **非真正的 uni-app 项目**：虽然项目名称包含 "uni-app"，但实际是标准的 Vue 3 + Element Plus Web 应用
- **无法编译为小程序**：缺少必要的 uni-app 依赖和配置
- **组件警告**：使用了 uni-app 组件语法但没有 uni-app 运行时支持

## 🔄 技术路线建议

### 已选择方案：方案 B - 真正迁移到 uni-app

**决策理由**：
- ✅ 支持多端部署（微信、支付宝、百度、字节跳动小程序）
- ✅ 符合原始需求
- ✅ 一套代码多端运行，降低长期维护成本
- ✅ 与现有Vue 3技术栈兼容

**需要做的**：
1. 安装所有 @dcloudio/* 依赖
2. 配置 uni-app 编译器
3. 移除 Element Plus 和 Vue Router
4. 重写所有页面和组件
5. 重新配置路由和状态管理
6. 适配小程序API
7. 配置 HTTPS 支持（小程序要求）

**工作量**：约2-3周（相当于重写前端）

### 其他方案对比

#### 选项 A：保持 Vue 3 Web 应用

**优点**：
- 当前代码基本可用
- Element Plus 生态成熟
- 开发效率高
- 维护成本低

**缺点**：
- 无法支持小程序部署
- 不符合原始需求

#### 选项 C：混合方案（不推荐）

**问题**：
- 技术栈更加混乱
- 维护成本极高
- 容易出错
- 不符合最佳实践

## 📋 开发规范

### 1. 组件使用规范
- **当前**：使用 Element Plus 组件（如 `<el-button>`, `<el-input>` 等）
- **避免**：使用 uni-app 组件（如 `<view>`, `<text>`, `<checkbox>` 等），会导致浏览器警告

### 2. 路由配置规范
- **使用**：Vue Router 进行路由管理
- **配置文件**：`src/router/index.js`

### 3. API 调用规范
- **使用**：Axios 进行网络请求
- **配置文件**：`src/api/request.js`

### 4. 代码风格规范
- **ESLint**：使用 ESLint 进行代码质量检查
- **Prettier**：使用 Prettier 进行代码格式化
- **命名规范**：
  - 组件：PascalCase（如 `MessageCard.vue`）
  - 变量：camelCase（如 `userName`）
  - 常量：UPPER_SNAKE_CASE（如 `API_BASE_URL`）

### 5. 多端兼容性考虑
- **如果选择迁移到 uni-app**：
  - 使用条件编译处理平台差异
  - 避免使用平台特定 API
  - 测试 H5 和小程序端运行效果

## 🔧 常见问题解决方案

### 1. 依赖冲突
- **解决方案**：使用 `--legacy-peer-deps` 安装依赖

### 2. 组件兼容性
- **解决方案**：优先使用 Element Plus 组件，避免使用 uni-app 组件

### 3. 路由配置
- **解决方案**：使用 Vue Router 配置页面路由，不要依赖 pages.json

### 4. API 调用
- **解决方案**：使用 Axios 进行网络请求，不要使用 `uni.request()`

### 5. 端口配置
- **后端**：使用 3001 端口（不是 3000）
- **前端**：使用 5173 端口

## 总结

项目当前是一个基于 Vue 3 + Element Plus 的 Web 应用，虽然名称包含 "uni-app"，但实际并非真正的 uni-app 项目。建议开发团队根据实际需求选择合适的技术路线：

1. **如果主要需求是 Web 端**：选择选项 A，保持 Vue 3 Web 应用，清理 uni-app 相关配置
2. **如果必须支持小程序**：选择选项 B，完全迁移到 uni-app，但需要重写前端代码

无论选择哪种方案，都应该保持文档和代码的一致性，确保开发团队对项目技术栈有清晰的理解。
