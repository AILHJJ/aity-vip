## 七、推送功能迭代入口

邮件/短信推送建议从整理后的新基线开始，不建议在当前脏目录直接开发。

推荐先做邮件，再做短信：

| 推送方式 | 推荐顺序 | 原因 |
| --- | --- | --- |
| 邮件 | 第一阶段 | 成本低、审批少、适合消息发布通知 |
| 短信 | 第二阶段 | 需要手机号、短信签名和模板审批、费用控制 |

推荐技术模型：

```text
管理员发布消息
  -> 后端写入 messages
  -> 写入 notification_outbox
  -> worker 异步发送邮件/短信
  -> 记录发送状态、失败原因、重试次数
```

不要在消息发布接口里同步调用外部邮件或短信服务，否则会让发布接口变慢，并增加失败回滚复杂度。

## 十一、推荐部署与版本管理规范

推荐采用“Git 管源码，构建产物走发布流程”的模型，而不是把所有东西都直接 `scp` 覆盖，也不是把服务器运行目录长期保持无 Git 状态。

推荐方案：

| 模块 | 源码管理 | 构建位置 | 发布方式 | 原因 |
| --- | --- | --- | --- | --- |
| 后端 API | Git，固定 `develop` 或新建 `release/production` | 服务器或本地均可，优先服务器安装生产依赖 | 服务器 `git pull` 或 `git fetch && git checkout <sha>` 后 `pm2 restart` | 后端需要可追踪提交和快速回滚 |
| 微信小程序 | Git 管理 `aity-uni-app-v2/` | 本地构建 | 微信开发者工具或 `miniprogram-ci` 上传 | 小程序发布不依赖服务器文件目录 |
| H5 | Git 管理源码，产物不进 Git | 本地构建 | SCP/rsync 上传到 `/var/www/html/h5` | 静态产物适合原子替换和备份 |
| 配置与密钥 | 不进 Git，只保留 `.env.example` | 服务器维护 | 通过运维手册记录字段，不记录值 | 避免再次泄露 token、密码和 JWT secret |

后端标准发布步骤建议：

```bash
cd /root/aity-vip-source

git fetch origin

git checkout <release-branch-or-sha>

cd backend
npm ci --omit=dev
npm run db:migrate   # 如果本次有迁移脚本，需先人工确认
pm2 restart aity-backend --update-env
curl https://aity88.online/api/health
```

H5 标准发布步骤建议：

```bash
cd aity-uni-app-v2

npm run build:h5

# 上传前在服务器备份

# 上传构建产物，建议使用 rsync；Windows 可用 scp 或 WinSCP
rsync -av --delete dist/build/h5/ root@124.221.119.134:/var/www/html/h5/
```

微信小程序标准发布步骤建议：

```bash

npm ci

# 用微信开发者工具导入 dist/build/mp-weixin，或用 miniprogram-ci 上传
```

准入规则：

| 规则 | 要求 |
| --- | --- |
| 先验证后提交 | 本地构建、接口冒烟、关键页面检查通过后再提交 Git |
| 提交范围要小 | 每次只提交本次验证过的代码和文档，不带目录整理残留 |
| 版本可观测 | 后端 `/api/health` 返回 `commit/buildTime/branch`，前端写入 `build-info.json` |
