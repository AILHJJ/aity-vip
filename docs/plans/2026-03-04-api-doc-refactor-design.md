## 一、背景和问题

### 1.1 现状分析

当前 `docs/api` 目录存在以下问题：

1. **版本混乱**
   - 金融数据接口有4个版本文档：
     - `连板天梯接口文档.md`
     - `金融行情数据接口文档.md`
     - `金融数据接口综合文档.md`
     - `金融数据接口最终文档.md`
   - 开发人员不知道哪个是最新版本

2. **格式混乱**
   - Markdown文档：10个
   - Excel文档：2个（`打板设计文档V1.3_何俊锋_20250306.xlsx`、`AI收评.xlsx`）
   - Python脚本：1个（`extract_api_info.py`）
   - Excel文件不便于Git版本控制和团队协作

3. **维护困难**
   - 多人协作时容易产生冲突
   - 缺少统一的文档结构规范
   - 没有明确的变更记录机制

### 1.2 使用场景

API文档需要支持以下场景：
- ✅ **前后端协作对接** - 前端开发根据文档调用接口
- ✅ **第三方集成** - 外部团队对接API
- ✅ **内部知识沉淀** - 团队文档库
- ✅ **自动化测试** - 基于文档生成测试用例

### 1.3 团队协作模式

- 多人协作维护：后端开发各自维护负责的接口文档
- 接口已存在：主要是文档整理和规范化工作

## 二、解决方案

### 2.1 核心策略：统一整合 + 单一真实来源

**原则**：
1. 每个领域只维护一个文档（单一真实来源）
2. 使用纯Markdown格式（Git友好）
3. 建立标准模板和规范
4. 提供工具辅助（自动生成索引）

### 2.2 目标文档结构

```
docs/api/
├── README.md                       # 总索引（自动生成）
│
├── 01-financial-data-api.md        # 金融数据接口（合并4个文档）
├── 02-trading-board-api.md         # 打板功能接口
├── 03-ai-assistant-api.md          # AI投顾接口
├── 04-core-business-api.md         # 核心业务接口
├── 05-sse-events.md                # SSE实时事件
│
├── templates/                       # 文档模板
│   └── api-doc-template.md
│
└── scripts/                         # 辅助工具
    └── generate-index.js           # 自动生成README索引
```

### 2.3 命名规范

**文件命名**：
- 格式：`数字前缀-模块名-api.md`
- 示例：`01-financial-data-api.md`
- 原因：数字前缀控制排序，便于查找

**锚点命名**：
- 格式：小写字母+短横线
- 示例：`#market-overview`（市场概览接口）
- 原因：兼容URL编码，便于跨文档引用

## 三、单文档标准结构

每个API文档必须包含以下章节：

### 3.1 文档头部

```markdown
# [模块名称] API文档

## 文档信息
- **版本**: v2.1.0
- **最后更新**: 2026-03-04
- **维护人**: @张三
- **变更日志**: 见文档底部
```

### 3.2 接口概览

```markdown
## 一、接口概览

| 接口名称 | 方法 | 路径 | 说明 |
|---------|------|------|------|
| 市场概览 | POST | /api/market/overview | 获取市场整体数据 |
| 涨跌分布 | POST | /api/market/distribution | 涨跌停分布统计 |
```

**目的**：
- 快速浏览所有接口
- 便于第三方集成评估
- 支持Ctrl+F快速查找

### 3.3 接口详情

每个接口包含以下子章节：

#### 3.3.1 基本信息
```markdown
**基本信息**
- **接口路径**: `http://123.60.27.66:7615/TQLEX?Entry=HQServ.PBHQInfo`
- **请求方法**: POST
- **Content-Type**: application/json
- **认证方式**: 无需认证
```

#### 3.3.2 请求参数
```markdown
**请求参数**
```json
{
  "Head": {
    "Target": 0
  },
  "Setcode": "1",
  "Code": "880005"
}
```

**参数说明**
| 参数名 | 类型 | 必填 | 说明 | 示例值 |
|--------|------|------|------|--------|
| Setcode | String | 是 | 市场代码 | "1" |
| Code | String | 是 | 指数代码 | "880005" |
```

#### 3.3.3 响应示例
```markdown
**响应示例**
```json
{
  "HQInfo": {
    "HQDate": "20260302",
    "Amount": "500000000000"
  }
}
```

**字段说明**
| 字段名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| HQDate | String | 行情日期 | "20260302" |
| Amount | String | 成交额（元） | "500000000000" |
```

#### 3.3.4 调用示例
```markdown
**调用示例**
```javascript
const response = await fetch('http://123.60.27.66:7615/TQLEX?Entry=HQServ.PBHQInfo', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    "Head": { "Target": 0 },
    "Setcode": "1",
    "Code": "880005"
  })
});
```
```

### 3.4 错误码说明

```markdown
## 三、错误码说明

| 错误码 | 说明 | 处理建议 |
|--------|------|----------|
| 400 | 参数错误 | 检查请求参数 |
| 401 | 未授权 | 检查认证token |
| 500 | 服务器错误 | 联系后端团队 |
```

## 五、文档维护规范

### 5.1 更新流程

```
1. 修改接口代码
2. 更新对应的API文档
3. 更新文档顶部的"最后更新"日期
4. 在"变更日志"添加变更记录
5. 提交代码和文档（同一commit）
```

### 5.2 版本号规范

遵循语义化版本控制（Semantic Versioning）：

- **主版本（Major）**: 不兼容的API变更
  - 示例：v1.0.0 → v2.0.0（删除旧接口，新增接口）
- **次版本（Minor）**: 向后兼容的功能新增
  - 示例：v2.0.0 → v2.1.0（新增板块异动接口）
- **修订号（Patch）**: 向后兼容的问题修复
  - 示例：v2.1.0 → v2.1.1（修复字段说明错误）

### 5.3 多人协作规则

**1. 文档职责分配**
- 每个文档指定主要维护人
- 修改他人维护的文档需先沟通

**2. Git提交规范**
```bash
# 提交格式
docs(api): 更新金融数据接口文档

- 新增板块异动接口说明
- 修复市场概览接口参数错误

Refs: #123
```

**3. 代码审查要点**
- 接口变更必须同步更新文档
- 检查变更日志是否记录
- 验证JSON示例格式正确

## 六、工具支持

### 6.1 自动生成索引脚本

**文件**: `scripts/generate-index.js`

**功能**:
- 扫描所有 `*-api.md` 文档
- 提取接口数量（通过"接口概览"表格行数）
- 提取最后更新时间（从文档头部）
- 提取维护人信息
- 自动更新 `README.md`

**使用方法**:
```bash
node scripts/generate-index.js
```

### 6.2 文档校验工具（可选）

**校验项**:
- ✅ 必填章节是否完整
- ✅ JSON示例格式是否正确
- ✅ 表格格式是否规范
- ✅ 链接是否有效
- ✅ 锚点是否唯一

## 七、实施计划

### 7.1 阶段一：准备工作（1小时）

1. **创建目录结构**
   ```bash
   mkdir -p docs/api/templates
   mkdir -p docs/api/scripts
   ```

2. **创建文档模板**
   - 编写 `templates/api-doc-template.md`
   - 包含所有必填章节
   - 提供填写示例

3. **编写自动生成索引脚本**
   - `scripts/generate-index.js`
   - 测试脚本功能

### 7.2 阶段二：文档合并（2-3小时）

1. **合并金融数据文档**
   - 合并以下4个文档：
     - `连板天梯接口文档.md`
     - `金融行情数据接口文档.md`
     - `金融数据接口综合文档.md`
     - `金融数据接口最终文档.md`
   - 输出：`01-financial-data-api.md`
   - 去重：删除重复接口
   - 排序：按功能模块分组

2. **整理打板功能文档**
   - 基于 `打板功能API接口文档.md`
   - 输出：`02-trading-board-api.md`
   - 补充：从Excel提取详细字段定义

3. **整理AI投顾文档**
   - 合并 `dify-workflow.md` 和 `AI收评.xlsx`
   - 输出：`03-ai-assistant-api.md`

4. **整理核心业务文档**
   - 基于现有的核心业务接口
   - 输出：`04-core-business-api.md`

5. **保留SSE文档**
   - 重命名：`sse-events.md` → `05-sse-events.md`
   - 补充标准结构

### 7.3 阶段三：清理和验证（30分钟）

1. **删除旧文档**
   ```bash
   # 备份旧文档（以防万一）
   mkdir -p docs/api/backup
   mv docs/api/*.md docs/api/backup/
   mv docs/api/*.xlsx docs/api/backup/

   # 移动新文档
   mv docs/api/0*.md docs/api/
   ```

2. **生成README索引**
   ```bash
   node docs/api/scripts/generate-index.js
   ```

3. **验证文档**
   - 检查所有链接是否有效
   - 验证JSON示例格式
   - 确认锚点可跳转

### 7.4 阶段四：团队培训（30分钟）

1. **编写维护指南**
   - 如何更新文档
   - 如何添加新接口
   - 如何使用自动生成工具

2. **团队同步**
   - 介绍新的文档结构
   - 分配文档维护责任人
   - 演示更新流程
