# 消息通知渠道抽象与运维告警架构设计

> 版本：v1.0（2026-09-15）
> 状态：方案定稿，待开发
> 目标：让 AI 自动化流程（发帖/回帖/讨论/通知/告警）**与具体 IM 渠道（企微/飞书/钉钉）解耦**，切换渠道只需换实现，业务逻辑零改动。

## 一、背景与目标

### 现状问题

1. **业务逻辑与企微强耦合**：`wecomBotService.js` 把「WebSocket 接入 + 指令解析 + 业务处理 + 主动推送」耦合在一起，无法复用到飞书/钉钉。
2. **运维告警缺乏体系**：目前只有 SSL 证书告警（acme.sh webhook + cron 脚本），缺服务崩溃、重启、磁盘、CPU 等预警。
3. **告警通道选型不清**：业务通知已切到智能机器人主动推送（webhook 下线），但运维告警的通道选型需要明确。

### 目标

1. **渠道抽象**：定义统一的渠道接口，业务逻辑（指令解析/发帖/回帖/讨论/绑定/通知组装）不感知具体渠道。
2. **双通道分工**：业务交互走 Bot 通道，运维告警走 Webhook 通道（带外告警）。
3. **渠道可插拔**：企微/飞书/钉钉通过 env 配置切换，新增渠道 = 新增一个实现类。

## 二、核心设计：双通道分工

```
┌──────────────────────────────────────────────────────┐
│                    业务层（渠道无关）                    │
│  - 指令解析 parseCommand                               │
│  - 发帖/回帖/讨论/绑定 业务处理                          │
│  - 通知内容组装 notifyNewDiscussion / notifyNewReply    │
└──────────────────┬───────────────────┬────────────────┘
                   │                   │
        ┌──────────▼─────────┐  ┌──────▼────────────────┐
        │ BotChannel（双向）   │  │ WebhookChannel（单向） │
        │  企微/飞书/钉钉各实现 │  │  企微/飞书/钉钉各实现   │
        └────────────────────┘  └───────────────────────┘
             业务交互 + 通知          运维告警（带外保命）
```

### 为什么运维告警用 Webhook 而不是 Bot？

| 维度 | Webhook | Bot 主动推送 |
|---|---|---|
| **独立性（关键）** | 直连渠道服务器，后端挂了照样告警 | 依赖后端进程 + 长连接，后端挂=告警挂 |
| 通用性 | 三渠道协议统一（HTTP POST），换 URL 即可 | 各渠道推送 API 差异大 |
| 轻量 | bash curl 一行 | 需维护长连接进程 |

**结论**：运维告警是「带外告警」，通道绝不能和故障源同一进程。服务挂了靠 bot 告警，则 bot 也挂，告警失去意义。因此运维告警固定走 **Webhook**，业务通知才走 **Bot**。

## 三、渠道接口设计

### 3.1 BotChannel（双向交互）

```js
// channels/BotChannel.js —— 接口契约
class BotChannel {
  name = 'base';           // 'wecom' | 'feishu' | 'dingtalk'

  start() {}               // 建立连接（WebSocket 长连接或事件订阅）
  stop() {}                // 关闭连接

  // 收消息：注册回调，收到群内指令消息时触发
  // handler(ChannelMessage) => Promise<void>
  onUserMessage(handler) {}

  // 被动回复（响应用户指令）
  reply(reqId, content) {}

  // 主动推送（业务通知用，如新帖/回帖）
  sendToGroup(content) {}  // 返回 boolean，是否发送成功

  // 图片下载解密（各渠道图片加密方式不同，需各自实现）
  async downloadImage(imageObj) {}  // 返回 { url, filename } 或 null
}

// 渠道无关的消息结构
// {
//   msgId: string,     // 消息唯一 ID（幂等去重）
//   userId: string,    // 用户标识（企微 userid / 飞书 open_id）
//   chatId: string,    // 群会话 ID（主动推送用）
//   chatType: string,  // 'group' | 'single'
//   msgType: string,   // 'text' | 'image' | 'mixed'
//   content: string,   // 文本内容（text/mixed 提取后）
//   images: any[],     // 图片对象（渠道原生格式）
// }
```

### 3.2 WebhookChannel（单向告警）

```js
// channels/WebhookChannel.js —— 接口契约（运维告警专用）
class WebhookChannel {
  name = 'base';  // 'wecom' | 'feishu' | 'dingtalk'

  // 发送告警：不依赖后端，独立于 BotChannel
  // 底层是 HTTP POST 到渠道 webhook URL，bash 脚本也可直接调用
  async sendAlert(content) {}
}

// 统一告警入口（后端内）：供 cron / 监控脚本调用
// POST /api/alert { token, title, level, content }
// → 后端转发到 WebhookChannel.sendAlert
```

### 3.3 业务核心（渠道无关）

```js
// services/botService.js —— 从现有 wecomBotService 抽离，去掉所有企微依赖
class BotService {
  constructor(channel) {
    this.channel = channel;           // 注入渠道实现
    this.pendingImages = {};
    this.processedMsgIds = new Set();
  }

  async handleMessage(msg) {          // 渠道无关的消息处理入口
    // 1. 幂等去重（msg.msgId）
    // 2. 图片缓存（msg.images → channel.downloadImage）
    // 3. parseCommand(msg.content)
    // 4. 身份校验 findBinding(msg.userId)
    // 5. 分发 handlePost / handleReply / handleCreateDiscussion / handleBind
    // 6. 回执 channel.reply(msg.reqId, text)
  }

  parseCommand(content) { ... }       // 纯函数，完全复用现有实现
  async handlePost(binding, parsed, images) { ... }   // 复用
  async handleReply(...) { ... }                       // 复用
  async handleCreateDiscussion(...) { ... }            // 复用
  async handleBind(...) { ... }                        // 复用
  async findBinding(userId) { ... }                    // 复用
}
```

## 四、现状 → 目标 迁移映射

| 现有文件 | 现状 | 目标 | 迁移动作 |
|---|---|---|---|
| `services/wecomBotService.js` | WebSocket 接入 + 指令解析 + 业务 + 推送 全耦合 | 拆成 2 层 | ①WebSocket 部分 → `channels/WecomBotChannel.js`；②指令解析/业务 → `services/botService.js`（注入 channel） |
| `services/wecomNotifyService.js` | 通知组装 + 主动推送（调 wecomBotService） | 保留通知组装，推送改调 BotChannel | 抽 `notifyService.js`（渠道无关），`sendText` 改调 `botService.channel.sendToGroup` |
| `utils/wecomImage.js` | 企微 AES 解密 + 格式检测 | 移到渠道实现 | 成为 `WecomBotChannel.downloadImage` 的内部逻辑 |
| `models/WecomUserBinding.js` | 企微 userid ↔ admin | 通用用户绑定 | 改字段 `channel` + `channelUserId`，兼容企微/飞书/钉钉 |
| `index.js` | `wecomBotService.start()` | 按 env 选渠道 | `botChannel = createBotChannel(env.IM_CHANNEL); botService = new BotService(botChannel)` |

## 七、运维告警体系（待建设）

### 告警事件清单

| 事件 | 检测方式 | 级别 | 通道 |
|---|---|---|---|
| 服务崩溃 | pm2 崩溃钩子 / 进程监控 | 严重 | webhook |
| 服务重启成功 | pm2 启动钩子 | 提示 | webhook |
| SSL 证书过期/续期失败 | acme.sh 钩子 + 周巡检 cron | 严重 | webhook |
| 磁盘满（>85%） | cron 脚本 | 警告 | webhook |
| CPU/内存持续高 | 监控脚本 | 警告 | webhook |
| 数据库连接失败 | 健康检查 | 严重 | webhook |

### 实施路径

1. 后端加统一告警 API：`POST /api/alert`（token 鉴权 + 转发 WebhookChannel）
2. pm2 钩子（`--on-crash` / 启动脚本）curl 告警 API
3. cron 巡检脚本（SSL/磁盘/CPU）curl 告警 API
4. 告警 API 里组装统一卡片格式（级别 emoji + 标题 + 时间 + 详情）
