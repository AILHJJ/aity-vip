# 飞书渠道接入改造评估

> 版本：v1.0（2026-09-15）
> 状态：评估完成，待立项
> 关联：《消息通知渠道抽象与运维告警架构设计.md》（渠道抽象是飞书接入的前置重构）

## 一、飞书机器人体系认知

飞书有两套机器人，对应企微的两套：

| 飞书 | 对应企微 | 能力 | 用途 |
|---|---|---|---|
| **自建应用机器人** | 智能机器人（API 模式） | 收消息 + 发消息 + 回复，双向 | 群内发帖/回帖/讨论 |
| **自定义机器人（群 webhook）** | 群机器人（webhook） | 单向推送 | 运维告警 |

### 飞书自建应用机器人的接入方式

飞书支持**两种**事件接收方式，和企微高度相似：

| 方式 | 说明 | 是否需要公网 |
|---|---|---|
| **WebSocket 长连接** ✅ | `@larksuiteoapi/node-sdk` 的 `WSClient`，`wsClient.start()` 建立连接 | 不需要 |
| HTTP 回调地址 | 需要公网 URL + 验签 | 需要 |

**我们选 WebSocket 长连接**（和企微长连接一致，无需公网回调，避免之前企微回调 URL 域名校验的坑）。

### 关键凭证

- `appId` + `appSecret`（飞书开放平台 → 自建应用 → 凭证与基础信息）
- 无需 Bot ID/Secret（企微特有）、无需 Token/EncodingAESKey（回调模式特有）

## 二、能力对照表（企微 vs 飞书）

| 能力 | 企微智能机器人（现状） | 飞书自建应用机器人 | 改造难度 |
|---|---|---|---|
| 建立连接 | `wss://openws.work.weixin.qq.com` + `aibot_subscribe` | `Lark.WSClient.start()`（官方 SDK） | ⭐ 简单，SDK 封装好 |
| 收消息 | `aibot_msg_callback`（msgid/chattype/from.userid/msgtype/text/image） | `im.message.receive_v1` 事件（message_id/chat_type/open_id/message_type） | ⭐⭐ 字段映射 |
| 主动发消息 | `aibot_send_msg`（chatid + markdown） | `client.im.message.create`（receive_id + msg_type + content） | ⭐⭐ 字段映射 |
| 回复消息 | `aibot_respond_msg`（req_id 透传） | `client.im.message.reply`（message_id 透传） | ⭐⭐ 字段映射 |
| 图片接收 | `image.url + image.aeskey`（AES 解密） | 图片给 `message_id`/`file_key`，需调 `im.v1.message_resource.get` 下载 | ⭐⭐⭐ 但**无 AES 解密**，更简单 |
| 群通知 webhook | 群机器人 webhook | 自定义机器人 webhook | ⭐ 简单 |
| 用户标识 | `userid`（明文） | `open_id`（应用内）或 `user_id`（租户内） | ⭐⭐ 绑定表存 open_id |
| 长连接限制 | 每应用 50 连接 | 每应用 50 连接；集群模式下多 client 随机一个收消息 | ⚠️ 单进程无影响 |

## 三、逐模块改造评估

### 3.1 通知推送（主动发消息）

- 现状：`wecomBotService.sendToChat(chatid, markdown)` → `aibot_send_msg`
- 飞书：`client.im.message.create({ receive_id_type: 'chat_id', receive_id: chatId, msg_type: 'text', content: ... })`
- 内容格式：企微用 markdown，飞书用 **text**（富文本需要 post 格式）。markdown 渲染两渠道语法略有差异，需适配。
- **工作量：0.5 天**（含内容格式适配）

### 3.2 群内收消息 + 指令解析

- 现状：`onMsgCallback` 解析 `body.msgtype`（text/image/mixed）→ 提取 content + images
- 飞书：`im.message.receive_v1` 事件，消息结构：
  - `message.message_type`（text/image/post/...）
  - `message.content`（JSON 字符串，如 `{"text":"..."}`）
  - 图片：`message.content` 里的 `image_key`
- **关键差异**：飞书 content 是**序列化的 JSON 字符串**，需先 JSON.parse 再取 text；图片需要额外 API 下载（`im.v1.message_resource.get`）。
- **指令解析逻辑（parseCommand）100% 复用**，只改消息提取层。
- **工作量：1~1.5 天**

### 3.3 图片处理

- 现状：企微图片 `url + aeskey` → 下载 → AES 解密 → 格式检测
- 飞书：图片给 `image_key` → 调 `im.v1.message_resource.get`（带 tenant_access_token）下载 → **直接是原图，无 AES 解密**
- **飞书比企微更简单**（省掉 AES 解密 + 32 字节 PKCS#7 那套坑）。
- **工作量：0.5 天**

### 3.4 身份绑定

- 现状：`wecom_user_bindings` 表（wecom_user_id ↔ admin_user_id）
- 飞书：用 `open_id`（应用内用户唯一标识）绑定。
- **通用化改造**：表加 `channel` + `channel_user_id` 字段（或新建通用表），兼容企微/飞书。
- **工作量：0.5 天**

### 3.5 运维告警 webhook

- 现状：SSL 告警走企微 webhook（独立机制）
- 飞书：自定义机器人 webhook，body 格式 `{"msg_type":"text","content":{"text":"..."}}`（与企微 `{"msgtype":"text","text":{"content":"..."}}` 类似）
- **工作量：0.5 天**（换 URL + body 格式适配）

## 四、工作量汇总

| 模块 | 工作量 | 累计 |
|---|---|---|
| 通知推送（主动发消息 + markdown→text 适配） | 0.5 天 | 0.5 天 |
| 群内收消息 + 指令解析（含 content JSON 解析） | 1~1.5 天 | 1.5~2 天 |
| 图片处理（下载，无解密） | 0.5 天 | 2~2.5 天 |
| 身份绑定（通用化） | 0.5 天 | 2.5~3 天 |
| 运维告警 webhook | 0.5 天 | 3~3.5 天 |

**总计约 3~3.5 天**（不含渠道抽象重构的 1~2 天）。

> 若先完成渠道抽象重构（见架构文档阶段 1），飞书接入只需写 `FeishuBotChannel` 一个实现类，**约 1~2 天**，且业务逻辑零改动。

## 五、迁移路径（推荐顺序）

```
阶段 A：渠道抽象重构（BotChannel 接口 + botService 抽离）
        → 企微切换到抽象层，功能回归验证
阶段 B：飞书接入（FeishuBotChannel 实现类）
        → env 切 IM_CHANNEL=feishu 即可切换
阶段 C：飞书运维告警 webhook
        → 换 ALERT_WEBHOOK_URL + body 适配
```

阶段 A 是**一次性投入**（1~2 天），之后飞书/钉钉接入都是"加一个实现类"的边际成本。

## 六、风险与坑（提前预警）

| 风险 | 说明 | 对策 |
|---|---|---|
| **markdown 渲染差异** | 企微 markdown 语法 ≠ 飞书 text/post 语法 | 通知内容组装层做渠道适配（各渠道模板） |
| **content 是 JSON 字符串** | 飞书消息 content 是序列化 JSON，需 parse | 消息提取层统一 parse |
| **图片下载需 token** | 飞书图片下载要 tenant_access_token | SDK 自动管理 token，无需手写 |
| **长连接集群模式** | 多 client 随机收消息 | 我们单进程，无影响 |
| **open_id vs user_id** | open_id 是应用内标识，换应用就变 | 绑定表用 open_id，与企微 userid 隔离 |
| **消息类型更丰富** | 飞书有 post/富文本/卡片等 | 首期只处理 text/image，其他类型忽略 |

## 七、结论

1. **飞书接入技术完全可行**，与企微能力高度对称，且**图片处理更简单**（无 AES 解密）。
2. **核心业务逻辑（指令解析/发帖/回帖/讨论/绑定）100% 复用**，只改接入层。
3. **建议先做渠道抽象重构**（架构文档阶段 1），让飞书/钉钉接入变成"加实现类"的边际成本。
4. 若不做抽象、直接复制一套飞书代码，工作量翻倍且后续维护两套逻辑，**不推荐**。
