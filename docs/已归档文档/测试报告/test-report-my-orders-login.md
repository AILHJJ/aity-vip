### 2.3 前端框架特性观察

#### 登录页面技术栈分析

**观察到的技术特点**:
1. **框架**: 可能使用 uni-app 或类似的跨平台框架
2. **输入框特性**:
   - 所有输入框默认带有 `readonly` 属性
   - 需要点击激活后才能输入
   - 直接使用 JavaScript 设置值可能无法触发框架的数据绑定
3. **验证码机制**:
   - 图形验证码: 在密码登录时出现
   - 短信验证码: 需要"获取验证码"操作
4. **协议确认**: 首次登录会弹出协议确认对话框

**自动化测试难点**:
- 输入框的 readonly 属性导致常规填充方法失效
- 框架的数据绑定机制需要特殊处理
- 验证码机制增加了自动化测试的复杂度

## 四、问题与建议

### 4.1 关键问题

#### 问题 1: 登录流程需要 APP 配合
**严重程度**: 高
**影响范围**: 所有测试用例

**描述**:
登录功能无法纯 Web 端完成,需要与移动 APP 配合。可能是以下原因之一:
- 短信验证码需要 APP 端同步
- 登录需要 APP 扫码确认
- 登录需要 APP 推送确认
- 账号安全策略要求多端验证

**建议解决方案**:
1. **测试环境配置**:
   - 提供测试专用的登录 API 或 token
   - 禁用测试环境的短信验证码要求
   - 配置测试账号的白名单机制

2. **测试策略调整**:
   - 使用 APP 自动化工具(如 Appium)配合测试
   - 手动登录后保存 session,后续测试复用
   - 开发 mock 接口绕过登录验证

---

#### 问题 2: 前端框架的数据绑定机制
**严重程度**: 中
**影响范围**: 登录功能测试

**描述**:
登录页面使用的前端框架(可能是 uni-app)对输入框有特殊处理:
- 输入框默认带 readonly 属性
- 直接使用 JavaScript 设置值无法触发框架的数据绑定
- 需要模拟真实的用户输入行为

**建议解决方案**:
1. 使用 `page.keyboard.type()` 逐字符输入
2. 使用 `page.locator().fill()` 并触发相关事件
3. 研究框架的 API,直接调用框架的数据绑定方法

---

#### 问题 3: 图形验证码验证机制
**严重程度**: 中
**影响范围**: 密码登录方式

**描述**:
密码登录时会出现图形验证码要求,但输入测试验证码后无法成功登录。

**建议解决方案**:
1. 测试环境配置万能验证码或禁用验证码
2. 提供验证码识别接口或 OCR 集成
3. 使用 cookie/token 绕过验证码检查
